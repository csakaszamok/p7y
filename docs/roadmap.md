# Purgatory roadmap

## Open, not yet scheduled

- **Optional hardening: keep ports published on all interfaces away from neighbouring sandboxes (foxglove image).** Today this is Docker's usual behaviour: `9000:9000` is reachable from other sandboxes on the DinD container's `traefik-net` address, `127.0.0.1:9000:9000` only through its tunnel (the starter stack already publishes this way, see [Isolation between sandboxes](networking.md#isolation-between-sandboxes)). To always close them instead of leaving it to the user: in the foxglove image (`dind` and `sysbox`), after dockerd starts, `iptables -I DOCKER-USER -i eth+ -m conntrack ! --ctstate RELATED,ESTABLISHED -j DROP` (and `ip6tables`). frpc connects from the inside, so the tunnels keep working. Afterwards the "by design" check in `tests/isolation.sh` has to be reversed.
- **Authentication for the frps API** (`:7500` through socat, today listing a sandbox's proxies without authentication). It is reachable from other sandboxes over `traefik-net`, not from outside. (The Purgatory API requires authentication, see [Web UI and sign-in](web-ui.md); the sandbox's Docker API requires its TLS client certificate.)
- **A Kata Containers runtime, for untrusted code.** Each sandbox in its own lightweight VM with its own kernel, so root inside a sandbox no longer means root on the host (today's `dind` runtime is `privileged`). Docker supports Kata through its containerd shim (`"runtimes": {"kata": {"runtimeType": "io.containerd.kata.v2"}}` in the host's `daemon.json`, then `runtime: kata` in the sandbox's compose service), so it fits next to `dind` and `sysbox` as a third runtime with the same wiring (FRP tunnel, Traefik route, Sablier, `docker_data` volume, archive). To work out:
  - the host needs hardware virtualization (KVM): bare metal, or a cloud VM with nested virtualization;
  - dockerd inside the Kata VM: `privileged` there applies to the VM only, not the host, but must not pass the host's devices through;
  - the `docker_data` volume and its performance (virtio-fs), and how the CPU and memory limits map to the VM's size;
  - a foxglove image for it, and the same integration tests as for the other runtimes;
  - still a *sandbox* (same API, lifecycle, quota and UI), with its isolation shown as a badge next to its name and chosen at create time ("Isolation: Container / MicroVM"): `dind` 🟠 **privileged**, `sysbox` 🔵 **container**, `kata` 🟢 **microVM**. "MicroVM" is said only where it is true: `dind` and `sysbox` sandboxes share the host's kernel.
- **GPUs in sandboxes.** Today no sandbox sees a GPU. A sandbox could ask for one at create time, like CPUs and memory, and the list, the panel and the API would show which have one (a *GPU* column with the model, e.g. `RTX 4090`). It suits the sleep model: a sleeping sandbox could give its GPU back, and the next one to wake take it. To work out:
  - per runtime: `dind` needs the NVIDIA driver and `nvidia-container-toolkit` on the host, the device passed to the sandbox container and the toolkit in the foxglove image, so the inner Docker hands it on to the apps; whether and how `sysbox` (the production runtime) passes GPUs through, to check first; Kata only through VFIO, typically one GPU per VM;
  - detecting the host's GPUs at startup and in `check-host.sh` (`nvidia-smi`, Docker's runtimes);
  - limits and quota (`SANDBOX_MAX_GPUS`, the admin beyond), as for CPU and memory;
  - a whole GPU per sandbox, or shared (time-slicing, MIG);
  - what a waking sandbox does when every GPU is taken: wait, refuse, or start without one.
- **To review: the path of a sandbox's traffic, without frp and without Purgatory.** Today there are two paths. Web addresses go Traefik → `<name>-socat:8080` → frps → tunnel → frpc → app: frpc registers every published port, so Traefik needs one fixed router per sandbox, and this keeps working while Purgatory is down. TLS TCP addresses (`-tcp`), Docker access (`-docker`) and SSH (`-shell-tcp`) go Traefik (TLS passthrough) → Purgatory's TCP gateway → the sandbox container's port on `traefik-net`: a port an inner container publishes is reachable there directly, without frp or a host port. So frp and socat are a design choice for the web path now, not a necessity, and the TCP path depends on Purgatory: while it is down or restarting (an upgrade), those addresses do not answer and open connections drop. What keeps a sandbox awake also differs: every web request; a `-docker` connection once a minute while it is open, whether or not anything goes through it (a Docker Desktop context of a sandbox keeps it awake forever); a `-tcp` connection not at all. To work out:
  - Purgatory writes Traefik's routes into `dynamic/` from the inner Docker (it already reads the published ports for the TCP addresses): an HTTP router per app address straight to `<name>:<port>`, and TCP routers with TLS for the `-tcp` addresses, so neither path goes through frp, socat or Purgatory, and each sandbox runs two containers fewer (frps, socat);
  - keeping what socat carries today: the Sablier middleware and group, a router that exists only while the sandbox runs (so a request to a sleeping one reaches the `p7y-wake` catch-all), and the health gate until the apps answer;
  - waking on a TCP connection, which needs someone to hold the connection while the sandbox starts (Purgatory today);
  - one rule for staying awake on every path: traffic in the last minute, not an open connection; Traefik's TCP routers have no Sablier middleware;
  - moving existing sandboxes over.
- **Teams:** a sandbox owned by a group, so several people see and manage it, and other teams do not; optionally a quota per team.
- **A hard disk quota per sandbox.** Today a sandbox above its disk limit is only flagged (see [Disk](resources.md#disk)). For a hard limit: its `docker_data` as a fixed-size ext4 image, loop-mounted through the local volume driver (`type=ext4`, `o=loop`); to work out: moving existing sandboxes' data, resizing (only while stopped), the archive, Docker Desktop. The Kata runtime gets this from its VM disk.
- **Kubernetes support:** move the runtime layer behind the Docker-specific code; Sablier's Kubernetes provider helps here.
