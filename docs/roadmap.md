# Purgatory roadmap

## Open, not yet scheduled

- **Optional hardening: keep ports published on all interfaces away from neighbouring sandboxes (foxglove image).** Today this is Docker's usual behaviour: `9000:9000` is reachable from other sandboxes on the DinD container's `traefik-net` address, `127.0.0.1:9000:9000` only through its tunnel (the starter stack already publishes this way, see "Isolation between sandboxes" in the README). To always close them instead of leaving it to the user: in the foxglove image (`dind` and `sysbox`), after dockerd starts, `iptables -I DOCKER-USER -i eth+ -m conntrack ! --ctstate RELATED,ESTABLISHED -j DROP` (and `ip6tables`). frpc connects from the inside, so the tunnels keep working. Afterwards the "by design" check in `tests/isolation.sh` has to be reversed.
- **Authentication for the frps API** (`:7500` through socat, today listing a sandbox's proxies without authentication). It is reachable from other sandboxes over `traefik-net`, not from outside. (The Purgatory API requires authentication, see "Web UI and sign-in" in the README; the sandbox's Docker API requires its TLS client certificate.)
- **Try `sysbox-sandbox` for real** on a Linux host with sysbox. The template already follows `dind-standard` (`foxglove:0.5.10-sysbox`, `runtime: sysbox-runc`, TLS from `daemon_json`), but so far only unit tests cover the generated configuration. To run: `tests/sablier-wake.sh` and `tests/archive.sh` with `DEFAULT_TEMPLATE=sysbox-sandbox`.
- **A Kata Containers runtime, for untrusted code.** Each sandbox in its own lightweight VM with its own kernel, so root inside a sandbox no longer means root on the host (today's `dind` runtime is `privileged`). Docker supports Kata through its containerd shim (`"runtimes": {"kata": {"runtimeType": "io.containerd.kata.v2"}}` in the host's `daemon.json`, then `runtime: kata` in the sandbox's compose service), so it fits next to `dind` and `sysbox` as a third runtime with the same wiring (FRP tunnel, Traefik route, Sablier, `docker_data` volume, archive). To work out:
  - the host needs hardware virtualization (KVM): bare metal, or a cloud VM with nested virtualization;
  - dockerd inside the Kata VM: `privileged` there applies to the VM only, not the host, but must not pass the host's devices through;
  - the `docker_data` volume and its performance (virtio-fs), and how the CPU and memory limits map to the VM's size;
  - a foxglove image for it, and the same integration tests as for the other runtimes;
  - still a *sandbox* (same API, lifecycle, quota and UI), with its isolation shown as a badge next to its name and chosen at create time ("Isolation: Container / MicroVM"): `dind` 🟠 **privileged**, `sysbox` 🔵 **container**, `kata` 🟢 **microVM**. "MicroVM" is said only where it is true: `dind` and `sysbox` sandboxes share the host's kernel.
- **Teams:** a sandbox owned by a group, so several people see and manage it, and other teams do not; optionally a quota per team.
- **A hard disk quota per sandbox.** Today a sandbox above its disk limit is only flagged (see "Disk" in the README). For a hard limit: its `docker_data` as a fixed-size ext4 image, loop-mounted through the local volume driver (`type=ext4`, `o=loop`); to work out: moving existing sandboxes' data, resizing (only while stopped), the archive, Docker Desktop. The Kata runtime gets this from its VM disk.
- **Kubernetes support:** move the runtime layer behind the Docker-specific code; Sablier's Kubernetes provider helps here.
