# Configuration

Main settings in `.env`:

| Variable | Default | Description |
|---|---|---|
| `ADMIN_TOKEN` | `abc123` (dev only) | Bearer token with admin rights on the API |
| `ADMIN_USER`, `ADMIN_PASSWORD` | `admin`, — | The local admin account of the UI |
| `SESSION_SECRET` | — | Signs the session cookie; a long random string |
| `HOST_DOMAIN` | `lvh.me` | Every address is under it: the UI, the registry, the sandbox apps (needs a wildcard DNS record) |
| `HOST_ADDRESS` | `localhost` | The host's address, put into the sandbox TLS certificates and used for the registry token URL when `PUBLIC_URL` is not set |
| `UI_HOST` | `p9m.<HOST_DOMAIN>` | The UI's own address, e.g. `console.example.com` with `HOST_DOMAIN=example.com`: the sandbox apps stay `<sandbox>-<subdomain>.example.com`. Under `HOST_DOMAIN`, the wildcard DNS record and certificate cover it. Set `PUBLIC_URL` to it too, and register its `/auth/callback` with the OIDC provider. A sandbox whose apps' addresses would include it (a sandbox `console` with `console-admin.example.com`) cannot be created |
| `PUBLIC_URL` | `http://<UI_HOST>` | The address of the UI as users see it; `https://…` turns on the HTTPS checks (see [HTTPS](https.md)) |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_PROVIDER_NAME` | — | Sign-in for everyone but the admin (see [Web UI and sign-in](web-ui.md)) |
| `OIDC_ALLOWED_DOMAINS`, `OIDC_ALLOWED_EMAILS` | — (anyone) | Who may sign in with OIDC, as comma lists: domains (`example.com,partner.org`, the exact domain, not its subdomains) and single addresses (`guest@gmail.com`). Without either, anyone with an account at the provider can sign in, with Google any Google account; Purgatorium says so in its log at startup. Checked at sign-in and on every request: someone taken off the list (after a restart) is signed out and their tokens stop working at once. The admin is never limited |
| `OIDC_ADMIN_EMAILS` | — (none) | Addresses (comma list) that are the admin when they sign in with OIDC in the browser, as the local admin is: all sandboxes, the Overview, users, no limits, host folders. They may sign in even if `OIDC_ALLOWED_*` leaves them out. Their tokens stay a user's. Taken off the list (after a restart), their session is a user's again at once. The local admin (`ADMIN_USER`) stays |
| `APPS_ACCESS_DEFAULT` | `public` | Who opens a sandbox app without a `p9m.access` label: `public`, `domain` (anyone who can sign in to Purgatorium) or `owner` (see [App access](app-access.md)) |
| `APP_ACCESS_SECRET` | generated into `data/app-access.key` | Signs the app access cookies and sign-in tickets |
| `HUB_ENABLED` | `false` | The [Hub](hub.md), the team's published apps at their own address: off unless `true`. |
| `HUB_HOST` | `hub.<HOST_DOMAIN>` | The Hub's address. |
| `HUB_ALLOWED_DOMAINS`, `HUB_ALLOWED_EMAILS` | (empty) | Who may look at the Hub besides the builders (`OIDC_ALLOWED_*`): viewers, who cannot sign in to Purgatorium itself. Empty: only builders. |
| `HUB_TITLE` | `Hub` | Shown in the Hub's header. |
| `SANDBOX_QUOTA` | `3` | Sandboxes a user may have running at once; asleep and deep-sleeping ones are not counted; `0` = unlimited |
| `SANDBOX_QUOTA_MAX` | (empty) | How many a user may have running while the server has room, above the guaranteed `SANDBOX_QUOTA` (e.g. `10`). Above the guarantee a new sandbox, or one woken, needs room to spare: every other owner must still be able to reach their guarantee (their running sandboxes hold their places already), and so must one newcomer. Waking from plain sleep takes no new place, so only this maximum counts. Nobody is ever put to sleep to make room. Empty: nothing above `SANDBOX_QUOTA`; `0`: no maximum |
| `FILES_MAX_UPLOAD` | `100m` | The largest file the **Files** tab (and `PUT /sandboxes/:name/files/content`) takes, like `512m` or `1g`. Every request body is read into memory first, so this (plus 1 MB) is also the cap on any request: a larger one gets 413 |
| `SANDBOX_MAX_TOTAL` | `200` (`setup.sh`: the suggested number for the host) | Running sandboxes on the whole server, the admin's included. The suggested number: twice as many as can all use their full `SANDBOX_CPUS` and `SANDBOX_MEMORY` at once (2 GB of memory kept for the rest), since most idle or sleep at any moment and a full server asks people to put theirs to sleep; at most as many as the disk holds at `SANDBOX_DISK` each. `setup.sh` writes it into a new `.env` in place of the example's 200, `check-host.sh` prints it, and the admin's Overview shows it under Host resources, with a warning when the limit set is well above it; asleep, deep-sleeping and archived ones take no place, so letting a sandbox sleep frees it for everyone. When it is reached nobody but the admin can create one or wake one: the admin is never refused, but its running sandboxes take places too; `0` = no limit. Each sandbox, asleep too, keeps a Docker network until it goes into deep sleep: the host's Docker address pools must have room for them (see `check-host.sh`) |
| `DEFAULT_RUNTIME` | `auto` | Runtime for new sandboxes when a request names none: `auto` picks `sysbox` where the host has sysbox installed (no privileged container) and `dind` otherwise; or name one (see [Runtimes and templates](runtimes-templates.md)) |
| `ALLOWED_RUNTIMES` | — (all) | Runtimes new sandboxes may use, as a comma list: `sysbox` forbids the privileged `dind` on a shared server. Others are left out of `GET /runtimes` and the **New sandbox** form, and a create asking for one is a 400 (so is one without a runtime when the default is not allowed). Existing sandboxes keep running, sleeping and waking |
| `SANDBOX_CPUS`, `SANDBOX_MEMORY` | `2`, `4g` | CPU and memory limit of every new sandbox (see [CPU and memory](resources.md#cpu-and-memory)) |
| `SANDBOX_MAX_CPUS`, `SANDBOX_MAX_MEMORY` | `4`, `8g` | How far a user can raise their sandbox's limits; the admin can go up to the host |
| `SANDBOX_MAX_IDLE_TIMEOUT`, `SANDBOX_MAX_DEEP_SLEEP_AFTER` | — (no limit) | How long a user's sandbox may stay awake without traffic, and asleep before deep sleep, at most (e.g. `2h`, `1d`); with a limit, *never* (`off`) is not allowed either. A template's longer default is cut to it; a sandbox that already has a longer value keeps it until it is changed. The admin is not limited |
| `SANDBOX_DISK` | `20g` | Disk use above which a sandbox is flagged; a warning only, see [Disk](resources.md#disk) |
| `HOST_MOUNT_ROOTS` | (empty: off) | Host folders the admin may mount into a sandbox, as a comma list of absolute paths (e.g. `/srv/shared,/data/projects`): a mount's host path must be one of them or under one (`/srv/shared2` is not under `/srv/shared`). Entries that are not absolute or have `..` are ignored, with a warning at startup; `/` (the whole host) is allowed, with a warning. **A mount gives whoever owns the sandbox that host folder, as root** (read-only if mounted so), and to every app in it. Empty: nobody can add a mount; ones already there stay until the admin removes them. See [Host folders](web-ui.md#host-folders) |
| `LOGIN_CAPACITY` | `on` | The sign-in page shows the sandbox places on the server: taken and free of `SANDBOX_MAX_TOTAL`, with a bar (orange from 90%, red when full). The page is public, so `off` hides it; nothing is shown without a server limit. Counted at most every 30 seconds |
| `GITHUB_STATS` | `on` | The topbar links to the GitHub repo and shows Purgatorium's version, stars and forks; the admin also sees when a newer release is out (one of the running series, else a later series). The server fetches the counts and the releases at most once an hour (users' browsers never contact GitHub, and nothing about the installation is sent); `off` never asks GitHub, and the link and the version stay |
| `USER_VIEW_SWITCH` | `false` | `true` gives users the **Simple \| Advanced** switch in the top bar (see [Simple and Advanced](web-ui.md#simple-and-advanced)). Otherwise users always see Simple, and `PUT /me/view` answers 403 to them; a view they chose before is kept for when it is turned on. The admin can always switch |
| `GITHUB_LINK` | `on` | `off` takes the GitHub card out of the topbar (and GitHub is never asked for the counts) |
| `UI_TITLE` | `Purgatorium` | The name at the top left, on the sign-in page and in the browser tab titles; `none` shows no name |
| `UI_LOGO` | Purgatorium's logo | The logo next to the name and the browser tab icon, on the Hub too: an `https://` address, or an image file in the container (`.svg`, `.png`, `.jpg`, `.webp`, `.gif`, `.ico`), e.g. `/app/data/logo.png` for `./data/logo.png`, served as `/assets/custom-logo`; `none` shows no logo. Its height is fixed, its width follows the image |
| `DEFAULT_TEMPLATE` | `starter` | Template for new sandboxes when a request names none. An old value such as `dind-standard` makes every create without a template fail with `Unknown template` |
| `DEEP_SLEEP_CHECK_INTERVAL` | `1m` | How often Purgatorium looks for sandboxes to take into deep sleep |
| `HOST_SANDBOXES_DIR` | auto-detected | Host path of `opt/sandboxes` (every sandbox's compose file mounts from it). Set it only if auto-detection fails |
| `P9M_API_BIND` | `0.0.0.0` | Interface of the direct API port `8081`; `127.0.0.1` for a public deployment |
| `P9M_VERSION` | the release the `docker-compose.yml` came from | The image version to run. Pin it only to stay on a version: an upgrade with a new `docker-compose.yml` then needs it changed too |
| `REGISTRY_PUBLIC_PULL` | `true` | Images whose versions all passed the secret scan can be pulled without a login; `false`: tokens only |
| `REGISTRY_CACHE_TTL` | `720h` (30 days) | How long the sandboxes' Docker Hub cache (`registry-cache`) keeps an image, counted from its **first** download: pulling it again does not extend it, so an image is downloaded again once its time is up, even in the middle of a workshop. In hours (`168h` = 7 days); `0` keeps everything for ever (the cache only grows: watch the disk). Not in hours (e.g. `7d`): the cache does not start, and the sandboxes pull from Docker Hub directly |
