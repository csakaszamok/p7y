# Web UI and sign-in

Purgatory has a small web UI (`http://p7y.<HOST_DOMAIN>`) for creating and managing sandboxes without the API directly, alongside the REST API.

Two ways to sign in:

- **Admin**: a local account, set via `ADMIN_USER` / `ADMIN_PASSWORD`. Signs in with the "Administrator sign-in" form and sees every sandbox (My sandboxes + All sandboxes).
- **Everyone else**: OIDC (Google or any OpenID Connect provider). Configure `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` and register the redirect URI `$PUBLIC_URL/auth/callback` with the provider — character for character (scheme, no trailing slash), under Google's *Authorized redirect URIs*, otherwise sign-in fails with `redirect_uri_mismatch`. Google accepts `http://` redirect URIs only for `localhost`, so with Google use an `https://` `PUBLIC_URL` (locally: a self-signed `*.lvh.me` certificate in `certs/` and `PUBLIC_URL=https://p7y.lvh.me`, see [HTTPS](https://csakaszamok.github.io/p7y/0.11/https/index.md)). `OIDC_PROVIDER_NAME` labels the sign-in button (default `Google`). Signed-in users only see their own sandboxes.

`SESSION_SECRET` signs the session cookie — set it to a long random string; sessions issued under an old value stop working if it changes.

Anyone with an account at the OIDC provider can sign in and create sandboxes, unless `OIDC_ALLOWED_DOMAINS` or `OIDC_ALLOWED_EMAILS` limits it (e.g. to `example.com`): with Google, set one of them, or any Google account gets in. An account not on the list is told so on the sign-in page; one taken off the list is signed out, and its tokens stop working, once Purgatory restarts with the new list. Each user may have `SANDBOX_QUOTA` sandboxes running at once (default 3, `0` = unlimited), guaranteed, and with `SANDBOX_QUOTA_MAX` more while the server has room to spare for the others' guarantees (*Running 4 / 3 · up to 10* beside **New sandbox**); asleep, deep-sleeping and archived ones are not counted, so letting a sandbox sleep frees its place, and the admin is not limited. At the limit a user can neither create a sandbox nor wake one, from sleep or deep sleep: its address shows *Running limit reached*, its address shows *Running limit reached* with the running sandboxes, and **Wake** in the panel lets the owner put one to sleep instead (`POST /sandboxes/:name/start` with `{"sleep": "<name>"}`). Purgatory never puts a sandbox to sleep on its own. Running sandboxes' web addresses do not go through Purgatory: they keep working while it is down; waking needs it, and so do the TLS TCP addresses and Docker access (they go through Purgatory's TCP gateway). `SANDBOX_MAX_TOTAL` (default 200) caps the running sandboxes on the whole server, the admin's included (asleep ones take no place): when it is reached nobody but the admin can create one or wake one (*The server is full*). The sign-in page shows the sandbox places above the sign-in buttons (taken and free; `LOGIN_CAPACITY=off` hides them), and once signed in the top bar does, on every page (e.g. *142 / 200 places*, the free ones on hover; orange from 90%, red when full). The **Overview** page shows the counts as cards: running of how many allowed, asleep, deep sleep and archived; for the admin the sandbox places used against the server limit (the admin's own sandboxes take places too), the host's CPU and memory (used now and reserved by running sandboxes), the disk use, a table per owner and a **Users** table. Users lists every account that has signed in since 0.10.2 (by e-mail; `admin` for the local admin): when it was last seen (a page load, at most every 10 minutes), its last sign-in and how many, its sandboxes now and created, and its last API use (its tokens); *no sandbox yet* marks someone who signed in but never created one. Owners of sandboxes from before have no dates. The rows are kept in `data/user-stats.json` until the admin deletes one (**Delete**: only the row; the account and its sandboxes stay). Only the admin sees them (`GET /users`, `DELETE /users/:account`).

From **Access tokens** (`/settings/tokens`), a signed-in user can mint a personal access token (`p7y_…`) for their own agents to use as `Authorization: Bearer p7y_…`; the token acts as that user for the API. The full token is shown once, at creation. Tokens can be set to expire in 30 days, 90 days, or never, and can be revoked at any time.

A token can also be limited to one sandbox (**Access** in the dialog, or **Token for this sandbox…** on a sandbox panel's **Access** tab). Such a token lists and opens only that sandbox, and can start, stop and restart it and change its sleep times; it cannot create or delete sandboxes or manage tokens (403), and any other sandbox answers 404. Deleting the sandbox leaves the token in place: if you restore the sandbox, it works again.

With such a token an agent can deploy and update apps in the user's sandbox: the Purgatory API gives it the sandbox's Docker client certificates, and the `docker` command line reaches the sandbox's own Docker daemon (or, in a sandbox from the `portainer` template, the Portainer API). Step by step: [agent guide](https://csakaszamok.github.io/p7y/0.11/agent-guide/index.md).

## Simple and Advanced

The top bar has a **Simple | Advanced** switch, remembered for each account (users start in Simple, the admin in Advanced). Users have it only with `USER_VIEW_SWITCH=true`; by default they stay in Simple, see [Configuration](https://csakaszamok.github.io/p7y/0.11/configuration/index.md). Simple is for people who only want their app online: the menu shows *My sandboxes* only; the list shows the name, status, *Sleeps in* and age; a new sandbox asks for a name and a template; a sandbox panel has **Wake** or **Sleep**, an **Apps** tab (the web address of each app and **Let your agent deploy…**: the Claude Code plugin or a zip for other agents, the same window as in Advanced, which adds its **Options**) and a **Details** tab (when it last ran, the sleep times, warnings, archiving). Advanced shows everything: Overview, tokens, SSH keys, the Terminal and Logs, and the Access, Files, Resources and Registry tabs. Simple only hides: what an account may do is the same in both, and the API and MCP do not change. `PUT /me/view` with `{"view": "simple"}` or `{"view": "advanced"}` sets it (403 for a user without `USER_VIEW_SWITCH=true`); `GET /me` returns it as `view`, and whether the account may switch as `view_switch`.

## Host folders

The admin can mount folders of the host into a sandbox, e.g. a shared data folder, when `HOST_MOUNT_ROOTS` lists where they may come from (e.g. `HOST_MOUNT_ROOTS=/srv/shared`; see [Configuration](https://csakaszamok.github.io/p7y/0.11/configuration/index.md)). On a sandbox panel's **Resources** tab, **Host folders** lists them, with **Remove** for each, and a form to add one: the host folder (at or under one of the roots), where it appears in the sandbox (empty: `/mnt/<last part of the host path>`) and **read-only**. The folder is bind-mounted into the sandbox container, so the apps in the sandbox's own Docker can bind it from there too (e.g. `/mnt/shared:/data`).

Adding or removing one recreates the sandbox container, after a confirmation: a running sandbox restarts (its apps are unreachable for a few seconds), an asleep one stays asleep, one in deep sleep gets the change when it wakes. A host folder that does not exist is not created: Docker refuses it, the panel shows Docker's message and nothing changes. The target cannot be `/`, a system directory (`/etc`, `/usr`, `/proc`, `/dev`, `/run`…) or on, above or under one of the sandbox's own mounts (`/var/lib/docker`, `/opt`, `/root`, `/home`, `/srv`, …). The mounts are kept in the sandbox's compose file (and its `p7y.mounts` label), so they survive sleep, deep sleep and upgrades.

**A mount gives whoever owns the sandbox that host folder**, as root, and every app and agent in it: mount read-only what they need not change, and only what they may see. The owner sees the list on the **Resources** tab, in Simple on **Details** (read-only); only the admin adds or removes them. With `HOST_MOUNT_ROOTS` unset no mount can be added; ones already there stay until the admin removes them. API: `GET`, `POST` and `DELETE /sandboxes/:name/mounts` (see [API](https://csakaszamok.github.io/p7y/0.11/api/index.md)), over MCP `list_sandbox_mounts`, `add_sandbox_mount` and `remove_sandbox_mount`.
